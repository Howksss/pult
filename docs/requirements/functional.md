# Функциональные требования

Требования выведены из процесса To-Be ([docs/bpmn](../bpmn/README.md)). В столбце «Шаг» указано, какой шаг процесса поддерживает требование.

Роли: **владелец проекта** настраивает граф и доступы, **разработчик** одобряет правки, **заказчик** следит за статусами и ставит задачи.

## Проекты и доступ

| ID | Требование | Шаг |
|---|---|---|
| FR-01 | Пользователь регистрируется и входит по email и паролю. | — |
| FR-02 | Владелец создаёт проект и привязывает к нему репозиторий GitHub пилотной системы. | — |
| FR-03 | Владелец приглашает участников в проект и назначает им роль: владелец, разработчик или заказчик. | — |

## Граф системы

| ID | Требование | Шаг |
|---|---|---|
| FR-04 | Владелец добавляет на граф блоки с типом (сервер, задание по расписанию, бот, интеграция, конфигурация, хранилище), именем и описанием. | 3 |
| FR-05 | Владелец соединяет блоки направленными связями с подписью и двигает блоки мышью. Раскладка сохраняется. | 3 |
| FR-06 | Владелец задаёт область доступа блока: список путей в репозитории (шаблоны glob) с правом на чтение или запись. | 4, 5 |
| FR-07 | Владелец настраивает проверки блока: тип (heartbeat, HTTP-запрос, шаблон ошибки в логе, код выхода задания), интервал и таймаут. | 1 |

## Мониторинг

| ID | Требование | Шаг |
|---|---|---|
| FR-08 | Pult принимает результаты проверок от probe на сервере клиента. Probe подтверждает подлинность токеном проекта. | 1 |
| FR-09 | Pult вычисляет статус блока по последним результатам его проверок: «работает», «предупреждение», «сбой». Если данных нет дольше трёх интервалов, ставится «нет данных». | 1 |
| FR-10 | Граф показывает статус каждого блока цветом и иконкой и обновляет статусы без перезагрузки страницы. | 2 |
| FR-11 | Когда блок переходит в «сбой» или восстанавливается, Pult отправляет участникам проекта уведомление в Telegram со ссылкой на блок. | 2 |
| FR-12 | Карточка блока показывает историю проверок, последние ошибки из логов и связанные задачи. | 3 |

## Задачи агенту

| ID | Требование | Шаг |
|---|---|---|
| FR-13 | Пользователь выбирает блок и ставит задачу текстом в чате блока. | 3 |
| FR-14 | Pult собирает контекст задачи: описание блока, последние результаты проверок, фрагменты логов, список файлов из области доступа. | 4 |
| FR-15 | Агент читает только файлы из области блока и пишет только в пути с правом на запись. Попытку выйти за область Pult отклоняет и записывает в журнал аудита. | 5 |
| FR-16 | Агент вносит изменения только в отдельной ветке клиентского репозитория и открывает pull request. В описании pull request — ссылка на задачу, причина сбоя, суть изменений и способ проверки. | 5 |
| FR-17 | Для ветки агента запускаются тесты пилотной системы, результат виден в задаче. Если тесты не прошли, агент дорабатывает правку. | 5 |
| FR-18 | Ответы агента появляются в чате по мере генерации. Пользователь может остановить задачу. | 5 |

## Проверка и развёртывание

| ID | Требование | Шаг |
|---|---|---|
| FR-19 | Разработчик видит diff pull request в Pult и одобряет его или возвращает агенту с комментарием. | 6 |
| FR-20 | Заказчик может одобрить pull request только для блоков типа «конфигурация» и только если владелец это разрешил. | 6 |
| FR-21 | Одобренный pull request сливается, CI/CD разворачивает обновление на сервер, затем Pult запускает внеочередную проверку блока. | 7 |
| FR-22 | После успешной проверки задача закрывается, а автор задачи получает уведомление. | 7 |
