# Нефункциональные требования

Каждое требование измеримо. В столбце «Как проверить» указан способ приёмки.

## Производительность

| ID | Требование | Как проверить |
|---|---|---|
| NFR-P1 | Граф из 100 блоков открывается не дольше 2 с (p95) на канале 10 Мбит/с. | Lighthouse / Performance в DevTools, 20 замеров |
| NFR-P2 | Новый статус блока появляется в интерфейсе не позже 5 с (p95) после получения результата проверки. | Метка времени результата и метка отрисовки в журнале клиента |
| NFR-P3 | Блок становится красным не позже двух интервалов проверки после сбоя (при интервале 60 с — не позже 2 мин). | Остановить задание на тестовом стенде, засечь время |
| NFR-P4 | Чтение графа и статусов через API: p95 не больше 300 мс при 50 одновременных пользователях. | Нагрузочный тест (k6 или Locust) |
| NFR-P5 | Первый фрагмент ответа агента появляется в чате не позже 10 с после отправки задачи. | Время между созданием задачи и первым событием потока |

## Доступность и надёжность

| ID | Требование | Как проверить |
|---|---|---|
| NFR-A1 | Доступность веб-интерфейса и API не ниже 99,5 % за месяц, то есть не больше 3,6 ч простоя. | Внешний мониторинг (Healthchecks / UptimeRobot) |
| NFR-A2 | Сбой Pult не влияет на пилотную систему. Probe только отправляет данные и не блокирует её процессы. При недоступности Pult probe буферизует результаты до 24 ч. | Остановить Pult на стенде: прогоны пилотной системы проходят, после восстановления буфер доставлен |
| NFR-A3 | Резервная копия базы делается ежедневно. Потеря данных не больше 24 ч (RPO), восстановление не дольше 4 ч (RTO). | Учебное восстановление из копии раз в месяц |

## Безопасность

| ID | Требование | Как проверить |
|---|---|---|
| NFR-S1 | Все 100 % попыток агента записать файл вне области блока отклоняются. | Автотесты на каждый инструмент агента с путями вне области, включая `../` и символические ссылки |
| NFR-S2 | Агент не делает ни одного прямого коммита в основную ветку клиентского репозитория. Правки идут только через pull request и сливаются после одобрения человеком. | Защита ветки main на GitHub; аудит коммитов по автору |
| NFR-S3 | Секреты не передаются в модель. Файлы `.env*`, `*.key`, `*.pem` исключены из контекста, строки, похожие на токены и пароли, маскируются. | Тест: файл с тестовым токеном в области блока не попадает в запрос к модели |
| NFR-S4 | Пароли хранятся как хеш Argon2id. Сессия — cookie HttpOnly + Secure сроком 7 дней. Весь трафик идёт по HTTPS, TLS не ниже 1.2. | Ревью кода, проверка SSL Labs не ниже A |
| NFR-S5 | Токен probe позволяет только отправлять результаты проверок своего проекта. | Тест: запрос с токеном probe к другим эндпоинтам возвращает 403 |
| NFR-S6 | Записи журнала аудита не редактируются и хранятся не меньше 1 года. | Права в БД: только INSERT и SELECT для роли приложения |

## Масштабируемость

| ID | Требование | Как проверить |
|---|---|---|
| NFR-M1 | Один экземпляр (2 vCPU, 4 ГБ RAM) обслуживает 20 проектов по 100 блоков при интервале проверки 60 с. | Нагрузочный тест с эмуляцией probe |
| NFR-M2 | Воркер агента масштабируется добавлением экземпляров: задачи берутся из очереди в БД, один экземпляр ведёт не меньше 3 задач одновременно. | Запуск двух воркеров, ни одна задача не выполняется дважды |
| NFR-M3 | Расход на модель ограничен: не больше 200 тыс. токенов на задачу. При превышении задача останавливается, пользователь видит сообщение об этом. | Учёт токенов в `task_message`, тест с искусственно низким лимитом |

## Удобство использования

| ID | Требование | Как проверить |
|---|---|---|
| NFR-U1 | Заказчик находит сломанный блок и ставит по нему задачу не больше чем за 3 действия с главного экрана. | Юзабилити-тест с пилотным заказчиком |
| NFR-U2 | Статусы различаются не только цветом, но и иконкой и подписью. Контраст текста не ниже 4.5:1. | Проверка в режиме эмуляции дальтонизма в DevTools |
| NFR-U3 | Интерфейс на русском языке, работает в двух последних версиях Chrome, Firefox и Edge. Статусы читаются на экранах от 360 px по ширине. | Ручная проверка по матрице браузеров |
