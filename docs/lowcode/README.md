# Low-code автоматизация

## Сценарий: ежедневная сводка для заказчика

Файл [daily-summary.n8n.json](daily-summary.n8n.json) — workflow для n8n из четырёх узлов:

1. **Каждый день в 09:00** (Schedule Trigger, cron `0 9 * * *`, часовой пояс Москвы).
2. **Граф проекта** (HTTP Request): `GET {PULT_URL}/api/v1/projects/{PULT_PROJECT_ID}/graph` из API v1.
3. **Текст сводки** (Code): отбирает блоки со статусом, отличным от «работает», и собирает текст.
4. **Отправить в Telegram** (Telegram): сообщение в чат заказчика.

Настройка: переменные окружения n8n `PULT_URL`, `PULT_PROJECT_ID`, `PULT_TELEGRAM_CHAT_ID` и учётные данные Telegram с токеном бота. Токен хранится в хранилище учётных данных n8n, а не в JSON workflow. Импорт: *Workflows → Import from file*.

Ограничение этой итерации: workflow подготовлен для импорта и в CI не запускается, сервера n8n у проекта пока нет. Контракт API, на который он опирается, проверяется тестами (`tests/test_contract.py`).

Это точка автоматизации A2 процесса To-Be ([docs/bpmn](../bpmn/README.md)) в «спокойном» варианте. Мгновенные оповещения о сбое реализованы в коде (#31), а сводку заказчик может настраивать сам.

## Low-code или код

Для сравнения взяты два способа уведомлять о статусах: сводка в n8n (этот сценарий) и мгновенные уведомления в коде (`app/integrations/telegram.py`, #31).

| Критерий | Low-code (n8n) | Код (Python в Pult) |
|---|---|---|
| Время создания | Минуты, мышью в редакторе | Час: код, тесты, ревью |
| Кто может изменить | Заказчик или аналитик: расписание, текст, получатели | Только разработчик |
| Тестирование | Ручной запуск в редакторе, автотестов нет | Модульные тесты без сети, проверка в CI |
| Версии и ревью | JSON экспортируется в git, но diff плохо читается | Обычный diff, ревью построчно |
| Надёжность | Зависит от отдельного сервиса n8n | Часть приёма данных, отказ отправки не ломает приём |
| Секреты | Хранилище учётных данных n8n | Переменные окружения Pult |
| Зависимость от платформы | Логика привязана к n8n | Нет |
| Подходит для | Отчёты, сводки, интеграции «на пробу», задачи, которые часто меняет заказчик | Критичные сценарии, которые входят в продукт и должны быть проверены |

Решение для Pult: всё, что влияет на реакцию на сбой (статусы, уведомления о сбое, задачи агенту), — в коде с тестами. Сводки и отчёты, которые заказчик хочет менять сам, — в low-code поверх стабильного API v1. Такое разделение работает благодаря контракту: low-code-сценарий зависит только от опубликованного API, а не от внутренностей Pult.
