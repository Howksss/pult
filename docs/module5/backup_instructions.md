# Резервное копирование и восстановление базы Pult

Инструкция для администратора, который видит проект впервые. Все команды выполняются на сервере от `root` в каталоге `/opt/pult` (клон репозитория). База — PostgreSQL 16 в контейнере `db` из `deploy/docker-compose.yml`, имя базы и пользователя `pult`.

## Что и когда копируется

| Копия | Расписание | Где лежит | Сколько хранится |
|---|---|---|---|
| ежедневная полная (`pg_dump`, формат custom, сжатие 6) | каждый день в 03:15 UTC (10:15 по Красноярску) | `/var/backups/pult/pult_<время>.dump` | 14 дней |
| еженедельная полная | воскресная ежедневная копия, жёсткая ссылка в `weekly/` | `/var/backups/pult/weekly/` | 8 недель |
| облачная | сразу после каждой копии | объектное хранилище S3, бакет `pult-backups`, папки `daily/` и `weekly/` | 14 дней и 8 недель |
| перед выкаткой | вручную перед `docker compose up` новой версии | `/var/backups/pult/pult_<время>_predeploy.dump` | 14 дней |

Скрипт — `deploy/db/backup-compose.sh`. Порядок шагов не меняется: снять копию во временный файл, проверить её читаемость (`pg_restore --list`), переименовать, отправить в облако и только потом удалять старые. Скрипт работает с `set -euo pipefail`, поэтому при сбое любого шага старые копии не удаляются.

```cron
15 3 * * * /opt/pult/deploy/db/backup-compose.sh >> /var/log/pult-backup.log 2>&1
0 4 1 * * /opt/pult/deploy/db/restore-check-compose.sh >> /var/log/pult-restore-check.log 2>&1
```

### Почему каждый день полная копия, а не разностная

Задание предлагает полную копию раз в неделю и инкрементальную или разностную раз в сутки. `pg_dump` делает только полные логические копии. Разностная копия в PostgreSQL требует физического копирования и архива WAL (`pg_basebackup --incremental` в версии 17, pgBackRest, WAL-G).

Мы делаем полную копию каждый день, потому что она дешёвая: база 71 МБ, сжатая копия 3,4 МБ, снимается за 1–2 с. Разностная копия нужна, когда полная копия долгая или занимает много места. У нас она восстанавливается за 6 с одним файлом, без сборки цепочки «полная + разностная». RPO такой же, как у разностной схемы (сутки), а восстановление проще и надёжнее. Недельные копии хранятся дольше ежедневных, чтобы можно было вернуться на два месяца назад.

Когда база вырастет до гигабайт или понадобится RPO в минутах, переходим на pgBackRest: полная физическая копия раз в неделю, разностная раз в сутки и непрерывный архив WAL.

### Правило 3-2-1

- **3 копии:** рабочая база, копия на диске сервера, копия в облачном хранилище.
- **2 разных носителя:** диск сервера и объектное хранилище S3 у другого провайдера.
- **1 копия вне площадки:** облачная. Если сервер потерян целиком, база восстанавливается из неё.

## Настройка облачной копии

Копии отправляет `rclone`. Ключи доступа к бакету лежат только на сервере, в репозитории есть шаблон без секретов `deploy/db/offsite.env.example`.

```bash
apt install rclone
install -m 600 deploy/db/offsite.env.example /root/.config/pult/offsite.env
nano /root/.config/pult/offsite.env        # адрес хранилища, ключ и секрет
set -a; . /root/.config/pult/offsite.env; set +a
rclone lsd "$OFFSITE_REMOTE"               # проверка доступа
```

Ключ выдаётся с доступом только к бакету копий. Скрипт читает файл сам: если его нет, копия остаётся только локальной, и в журнале это видно по отсутствию строк `rclone`.

## Ручные команды

```bash
deploy/db/backup-compose.sh                         # снять копию сейчас, вывод — путь к файлу
FORCE_WEEKLY=1 deploy/db/backup-compose.sh          # то же и положить в недельные
deploy/db/restore-check-compose.sh                  # развернуть последнюю копию во временную базу и сверить с рабочей
deploy/db/restore-check-compose.sh <файл.dump>      # то же для конкретной копии
ls -lt /var/backups/pult | head                     # последние копии
rclone ls "$OFFSITE_REMOTE/daily" | tail            # копии в облаке
```

`restore-check-compose.sh` разворачивает копию в базу `pult_restore_check`, запускает `verify.sh` и удаляет временную базу. `verify.sh` сравнивает:

- структуру: хэш `pg_dump --schema-only` обеих баз;
- число строк во всех таблицах. Строки, появившиеся в рабочей базе после снятия копии (идентификатор больше максимального в копии), не учитываются;
- версию схемы Alembic.

При расхождении скрипт завершается с кодом 1.

## Восстановление после сбоя

Ситуация: база повреждена или удалены данные, сервер жив.

1. Остановить запись: `docker compose -f deploy/docker-compose.yml stop api worker`.
2. Выбрать копию: последнюю из `/var/backups/pult`, а если сервер новый — скачать из облака: `rclone copy "$OFFSITE_REMOTE/daily/<файл>" /var/backups/pult/`.
3. Проверить копию: `deploy/db/restore-check-compose.sh <файл>`. Код возврата 0 — копия цела.
4. Сохранить повреждённую базу и развернуть копию на её место:

   ```bash
   docker compose -f deploy/docker-compose.yml exec -T db psql -U pult -d postgres \
     -c "ALTER DATABASE pult RENAME TO pult_broken"
   docker compose -f deploy/docker-compose.yml exec -T db createdb -U pult pult
   docker compose -f deploy/docker-compose.yml exec -T db pg_restore -U pult --no-owner --exit-on-error -d pult < <файл>
   ```

5. Если копия старше текущей версии кода, догнать схему: `docker compose -f deploy/docker-compose.yml run --rm migrate`.
6. Запустить сервисы: `docker compose -f deploy/docker-compose.yml up -d`, затем `deploy/smoke.sh`.
7. Записать инцидент: время копии, потерянный интервал, причину. Через неделю удалить `pult_broken`.

Ситуация: сервер потерян. Поднять новый сервер по [инструкции развёртывания](../deploy/README.md), положить `offsite.env`, скачать последнюю копию из облака и выполнить шаги 3–6.

## RPO и RTO

| Показатель | Значение | Обоснование |
|---|---|---|
| RPO (сколько данных можно потерять) | 24 ч | Копия раз в сутки. Конфигурация проектов, блоков и проверок меняется редко, и её можно повторить по истории задач. Результаты проверок probe присылает заново, после восстановления история продолжится с момента сбоя. Потеря суток истории не останавливает работу клиента |
| RTO (за сколько восстановиться) | 4 ч | Восстановление на живом сервере занимает около 30 мин: сама копия разворачивается за 6 с, остальное — ручные шаги и проверка. 4 ч заложены на худший случай, когда сервер потерян и нужен новый: заказ VPS, Docker, клон репозитория, копия из облака. Pult только наблюдает за системой клиента, сама система за это время продолжает работать |

Значения совпадают с требованием [NFR-A3](../requirements/non_functional.md). Если понадобится RPO меньше суток, следующий шаг — архив WAL (pgBackRest или WAL-G) с восстановлением на момент времени.

## Проверка копий

- **В CI** на каждый pull request (задание `database`): копия тестовой базы, восстановление и `verify.sh`.
- **На сервере** первого числа каждого месяца по cron: `restore-check-compose.sh` на последней копии. Журнал — `/var/log/pult-restore-check.log`.
- **Перед выкаткой** — копия `_predeploy`, проверка её читаемости встроена в скрипт.

Результат последней ручной проверки — в [backup_check.md](backup_check.md).
