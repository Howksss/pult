## Сверка модели и схемы

С практической работы № 2 схема прошла миграции `0003`–`0006`, а диаграмма осталась прежней. Расхождения, исправленные в диаграмме:

- нет таблицы `user_session` (сессии входа, `0006`);
- нет столбцов `project.probe_token_hash` (`0003`), `health_check.name`, `config`, `enabled`, `check_result.error_kind`, `details` (`0004`);
- первичные ключи нарисованы как `bigint`, а в схеме `integer`; координаты блока — `real`, а в схеме `double precision`.

Чтобы диаграмма больше не отставала, тест `test_er_diagram.py` разбирает `er_diagram.puml` и сравнивает с моделями таблицы, столбцы, типы и обязательность. Тест `test_schema_after_migrations_matches_models` сравнивает модели со схемой, которую строят миграции. Получается цепочка «диаграмма = модели = схема», и любой разрыв роняет CI.

## Типы данных

| Тип | Где | Почему |
|---|---|---|
| `integer` | все первичные и внешние ключи | 2,1 млрд значений. Самая быстрорастущая таблица `check_result` получает около 11,5 тыс. строк в сутки (8 проверок раз в минуту): запаса хватит на сотни лет. Когда проверок станет больше тысячи, ключ `check_result.id` переводится на `bigint` отдельной миграцией |
| `varchar(n)` | имена, почта, репозиторий, путь, цель проверки, код ошибки | Длина — правило предметной области, которое видит пользователь: имя блока до 100 символов, почта до 255, путь до 300. API проверяет ту же длину и отвечает 422, база — последний рубеж |
| `text` | описания, сообщение результата | Свободный текст без естественного предела. В PostgreSQL `text` и `varchar` хранятся одинаково, разница только в ограничении длины |
| `char(40)` | `deployment.commit_sha` | Хэш коммита всегда 40 символов, формат дополнительно проверяет `CHECK` |
| `varchar(64)` | хэши токенов | SHA-256 в шестнадцатеричном виде — ровно 64 символа |
| `timestamptz` | все моменты времени | Сервер работает в UTC, пользователи в Красноярске (UTC+7), probe клиента — в своём поясе. `timestamptz` хранит момент, а не показания часов, поэтому «сбой с 14:05» одинаков для всех |
| `double precision` | `block.pos_x`, `pos_y` | Координаты на холсте дробные после перетаскивания, точность до пикселя не важна |
| `boolean` | `health_check.enabled` | Флаг «включена или нет» |
| `jsonb` | `health_check.config`, `check_result.details`, `task_message.content`, `audit_event.payload` | Состав полей зависит от метода проверки или инструмента агента. Объём ограничен: `details` до 8000 символов JSON |
| `ENUM` | роли, типы блоков, статусы, методы | Набор значений фиксирован. База отвергает неизвестное значение, а не только API. Значения расшифрованы в словаре данных |
| `numeric(12, 2)` | `accounts.balance` в учебном примере | Денежные суммы хранятся точно, без ошибок округления `float`. В самом Pult денежных полей нет |

## Ограничения целостности

| Вид | Сколько | Примеры правил |
|---|---|---|
| `PRIMARY KEY` | 15 | у каждой таблицы, у `project_member` составной: человек входит в проект один раз |
| `FOREIGN KEY` | 17 | `CASCADE` для подчинённых данных (блоки проекта, проверки блока, результаты проверки); `RESTRICT`, если удаление уничтожит историю (автор задачи, автор ревью, автор записи аудита); `SET NULL` для аудита при удалении блока |
| `UNIQUE` | 7 + частичный индекс | почта пользователя, имя блока в проекте, одна связь между блоками в одну сторону, один pull request на задачу, одна идущая выкатка на pull request |
| `CHECK` | 24 | таймаут проверки не больше интервала, путь агента не выходит за репозиторий, выкатка не заканчивается раньше начала, у завершённой выкатки есть время окончания |
| `NOT NULL` | 69 из 87 столбцов | обязательные поля; необязательные (описание, время окончания, ревьюер) пусты, пока событие не наступило |

Полный перечень с определением и правилом для каждого ограничения — в [словаре данных](data-dictionary.md). Пояснения хранятся в самой базе (`COMMENT ON CONSTRAINT`), тест `test_every_table_column_type_constraint_and_index_is_commented` не даст добавить ограничение без пояснения. Отдельные тесты проверяют, что база действительно отвергает нарушения: `test_domain_rules_are_enforced_by_database` и соседние в `test_pg_schema.py`.

Правило «у проекта всегда есть владелец» нельзя выразить через `CHECK`: оно касается нескольких строк. Его держит API (`ensure_owner_remains`, ответ 409).

## Миграции

| Миграция | Что делает | Шаг по заданию |
|---|---|---|
| `0001_initial_schema` | все таблицы ПР2 с ключами, `NOT NULL`, базовыми `UNIQUE` и `ENUM` | создание таблиц |
| `0002`–`0006` | представление статуса, токен probe, диагностика, уникальность области, сессии | развитие схемы между ПР2 и ПР5 |
| `0007_domain_constraints` | 23 правила `CHECK`, уникальность связи, одна идущая выкатка, `RESTRICT` для авторов | ограничения |
| `0008_query_indexes` | индексы под запросы, удаление лишних | индексы |
| `0009_schema_comments` | `COMMENT ON` для таблиц, столбцов, типов, ограничений и индексов | словарь данных |
| `0010_seed_demo` | тестовые данные по флагу `-x seed=demo` | тестовые данные |

Схема с тестовыми данными на пустой базе — одна команда:

```bash
cd backend
DATABASE_URL=postgresql+psycopg://pult:<пароль>@localhost:5432/pult alembic -x seed=demo upgrade head
```

Миграции `0001`–`0006` уже применены на рабочем сервере, поэтому не переписывались. Новые ограничения добавлены отдельной миграцией. Перед этим проверено, что данные рабочей базы им не противоречат. Воспроизводимость проверяет CI: та же команда на второй пустой базе, затем `deploy/db/verify.sh` сравнивает структуру (хэш `pg_dump --schema-only`) и число строк во всех таблицах. Новые миграции откатываются до `0006` и применяются снова.

## Индексы

| Индекс | Какой запрос ускоряет |
|---|---|
| `ix_block_project_id` | блоки проекта: граф `GET /projects/{id}/graph` |
| `ix_health_check_block_id` (новый) | проверки блока `GET /blocks/{id}/checks`, расчёт статусов графа, каскадное удаление проверок при удалении блока |
| `ix_check_result_check_time` | последний результат и история проверки: `v_block_status`, панель проверок, начало сбоя ([анализ](../data/queries.md)) |
| `ix_check_result_checked_at_brin` | выборки результатов за период |
| `ix_project_member_user_id` (новый) | проекты пользователя `GET /auth/me`, `GET /projects`: первичный ключ `(project_id, user_id)` этот запрос не покрывает |
| `ix_block_link_target_block_id` (новый) | каскадное удаление связей блока-приёмника. По источнику ищет уникальный индекс `(source_block_id, target_block_id)` |
| `ix_agent_task_block_id`, `ix_task_message_task_id`, `ix_audit_event_block_id` | каскадное удаление и обнуление ссылок при удалении блока, чат задачи |
| `uq_deployment_one_running` | не ускоряет, а запрещает вторую идущую выкатку одного pull request |

Удалены как лишние: `ix_block_scope_block_id` (его покрывает уникальный индекс `(block_id, path_glob)`) и `ix_user_session_user_id` (сессию ищут только по хэшу токена). Не созданы, пока нет запросов: индексы по `agent_task.author_id`, `change_request.reviewer_id`, `deployment.change_request_id`. Они появятся вместе с кодом агента.

## Транзакции в коде

- Сессия запроса (`app/db.py`) при любой ошибке явно вызывает `rollback()`: незавершённые изменения не попадают в базу. Тест `tests/test_db.py`.
- Многошаговые операции фиксируются одним `commit()`: проект и его владелец (`create_project`), пачка результатов probe и пересчёт статусов (`record_results`).
- Сетевые вызовы вынесены за пределы транзакции. Ручной запуск проверки держал транзакцию открытой, пока ждал ответа проверяемого сервиса (до 60 с). Теперь чтение фиксируется до запроса, а запись результата идёт отдельной короткой транзакцией. Тест `test_run_now_does_not_hold_a_transaction_during_the_network_call`. Так же уведомление в Telegram отправляется после фиксации результатов: если оно не дошло, результаты уже сохранены.
- Нарушение уникальности превращается в ответ 409 с откатом (`commit_or_conflict`), а не в ошибку 500.
