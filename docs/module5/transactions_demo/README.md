# Транзакции и уровни изоляции

Учебный сценарий перевода денег между счетами двух пекарен. Он не входит в схему Pult и разворачивается в отдельной базе, чтобы не смешивать учебные таблицы с рабочими.

- [setup.sql](setup.sql) — таблицы `accounts` и `transfer_log`. Баланс `numeric(12, 2)` с ограничением `accounts_balance_not_negative CHECK (balance >= 0)`, журнал переводов ссылается на счета внешними ключами.
- [demo.py](demo.py) — открывает две настоящие сессии `psql` (A и B), подаёт им команды по очереди и записывает вывод. Протоколы ниже получены этим скриптом на PostgreSQL 16.10.

```bash
createdb bank_demo
python docs/module5/transactions_demo/demo.py bank_demo
```

## 1. Успешный перевод и COMMIT

[01_commit.txt](01_commit.txt). Списание 300 со счёта 1, зачисление на счёт 2 и запись в журнал выполняются в одной транзакции. После `COMMIT` балансы 700 и 800, в журнале одна запись. Сумма денег в системе не изменилась: 1500.

## 2. Сбой посреди транзакции и ROLLBACK

[02_rollback.txt](02_rollback.txt). Со счёта 1 уже списано 200: внутри транзакции сессия A видит баланс 500. Сессия B в этот момент видит прежние 700: незафиксированные изменения чужой транзакции не видны (грязного чтения нет). Затем запись в журнал падает: счёта 3 не существует, нарушен внешний ключ. После ошибки PostgreSQL отвергает любые команды транзакции (`current transaction is aborted`). `ROLLBACK` возвращает базу к состоянию до перевода: 700 и 800, в журнале по-прежнему одна запись. Списание без зачисления не сохранилось.

## 3. Нехватка средств и CHECK

[03_check.txt](03_check.txt). Перевод 5000 при балансе 700: зачисление прошло, но списание дало бы −4300 и нарушило `accounts_balance_not_negative`. База отвергла строку сама, приложению не нужно отдельно проверять остаток. После `ROLLBACK` балансы не изменились, зачисление тоже отменено.

## 4. Read Committed: неповторяющееся чтение

[04_read_committed.txt](04_read_committed.txt). Сессия A в транзакции уровня Read Committed читает баланс счёта 1 — 1000. Сессия B добавляет 100 и фиксирует изменение. A читает тот же счёт ещё раз в той же транзакции и получает 1100. Два одинаковых запроса в одной транзакции вернули разное: это неповторяющееся чтение.

Механизм: в Read Committed снимок данных берётся заново **для каждого запроса**. Второй запрос видит всё, что было зафиксировано до его начала.

## 5. Repeatable Read: чтение повторяется

[05_repeatable_read.txt](05_repeatable_read.txt). Тот же сценарий на уровне Repeatable Read. A читает 1100, B добавляет 100 и фиксирует, A снова читает — по-прежнему 1100. После завершения транзакции A видит 1200.

Механизм: в Repeatable Read снимок берётся **один раз**, при первом запросе транзакции, и действует до её конца (MVCC). Если A пытается изменить строку, которую после её снимка изменила B, PostgreSQL отвечает `could not serialize access due to concurrent update`. Это не сбой: так база не даёт перезаписать чужое изменение по устаревшему снимку. Приложение должно повторить транзакцию целиком.

## Что из этого используется в Pult

- По умолчанию в Pult уровень Read Committed. Запросы на чтение графа и проверок атомарны по одному запросу, а повторного чтения одной строки в транзакции нет.
- Многошаговые записи идут одним `commit()`, ошибка ведёт к явному `rollback()` ([раздел «Транзакции в коде»](../README.md#транзакции-в-коде)).
- Правила вроде «таймаут не больше интервала» держит `CHECK` в базе, как остаток счёта в этом примере.
