# Бизнес-процесс сопровождения пилотной системы

Пилотная система автопланирования выпечки работает на VPS по расписанию. Каждое утро она берёт продажи из POS-системы, учитывает погоду и праздники, собирает Excel-планы для каждой пекарни и рассылает их управляющим через Telegram-бота. Сопровождает её один разработчик.

## As-Is: как сбой устраняется сейчас

Схема: [as_is.bpmn](as_is.bpmn), изображение: [as_is.png](as_is.png).

Дорожки: «Заказчик (управляющий сети)», «Разработчик», «Сервер пилотной системы».

1. В 08:00 cron запускает расчёт плана. Если прогон прошёл, планы уходят управляющим. Если упал, бот присылает в Telegram короткое сообщение об ошибке.
2. Заказчик получает уведомление или сам замечает проблему в плане (пустая строка, странное число) и описывает её разработчику в мессенджере.
3. Разработчик уточняет детали, подключается к серверу по SSH, читает логи и ищет, какой компонент сломался: прогон, бот, POS-система, погода, шаблон Excel или настройки.
4. Разработчик правит код или конфигурацию, проверяет правку локально (dry-run, тесты), отправляет её в репозиторий, обновляет код на сервере и вручную перезапускает прогон.
5. Заказчик проверяет новый план. Если проблема осталась, цикл повторяется с шага 2.

### Узкие места и потери

| Где | Что теряется |
|---|---|
| Шаг 2 | Заказчик не видит, какой компонент сломан. Описание в свободной форме, без логов и без указания блока. |
| Шаги 2–3 | Задача ждёт, пока разработчик освободится. Это единственный исполнитель, и ночью и в выходные реакции нет. |
| Шаг 3 | Компонент ищется вручную по логам на сервере, это 30–90 минут на каждый сбой. |
| Шаг 4 | Правка уходит на сервер вручную. Нет обязательного ревью, откатывать тоже приходится руками. |
| Шаг 5 | Заказчик узнаёт об исправлении только из сообщения разработчика. Истории сбоев нет. |

## To-Be: процесс с Pult

Схема: [to_be.bpmn](to_be.bpmn), изображение: [to_be.png](to_be.png).

Дорожки: «Заказчик», «Pult», «ИИ-агент», «Разработчик».

1. Pult раз в минуту собирает результаты проверок блоков: heartbeat от probe на сервере, коды выхода заданий cron, шаблоны ошибок в логах, доступность внешних API. **[автоматизация]**
2. Если блок перешёл в «сбой», Pult подсвечивает его красным на графе и присылает уведомление в Telegram. **[автоматизация]**
3. Заказчик открывает граф, выбирает красный блок и ставит задачу в чате этого блока.
4. Pult собирает контекст задачи: описание блока, последние результаты проверок, фрагменты логов, файлы из области доступа блока. **[автоматизация]**
5. ИИ-агент анализирует причину, готовит правку в отдельной ветке клиентского репозитория и запускает тесты. Если тесты упали, он исправляет правку. Когда тесты проходят, агент открывает pull request с описанием причины и изменений. **[автоматизация]**
6. Разработчик просматривает diff и одобряет pull request или возвращает его с комментарием.
7. Pult сливает одобренный pull request, CI/CD разворачивает обновление на сервер, Pult повторно проверяет блок. Когда блок снова зелёный, заказчику приходит уведомление. **[автоматизация]**

### Точки автоматизации

| № | Что автоматизируется | Какую потерю убирает |
|---|---|---|
| A1 | Сбор статусов блоков | Ручной поиск сломанного компонента по логам |
| A2 | Уведомление со ссылкой на конкретный блок | Описание проблемы в свободной форме |
| A3 | Сбор контекста задачи | Уточнение деталей у заказчика |
| A4 | Подготовка правки и тестов агентом | Ожидание, пока освободится разработчик |
| A5 | Слияние, развёртывание и повторная проверка | Ручное обновление сервера и ручная проверка результата |

Решения остаются за человеком: заказчик решает, ставить ли задачу, разработчик — одобрить ли правку. Агент не пишет на сервер напрямую ([ADR 002](../adr/002_agent_changes_via_pull_request.md)).
