# Представление статуса и анализ запросов

## Представление `v_block_status`

Создаётся миграцией `0002_block_status_view`. Для каждого блока считает статус по тем же правилам, что и `app/services/status.py`:

- берётся последний результат каждой проверки блока;
- результат старше трёх интервалов проверки или его отсутствие означает «нет данных»;
- статус блока — худший из статусов проверок: `fail > warn > unknown > ok`;
- блок без проверок получает «нет данных».

Совпадение SQL и Python проверяет тест `tests/test_pg_status_view.py`: 9 сценариев на PostgreSQL, сравнивается вывод представления и `block_status`.

```sql
SELECT name, status FROM v_block_status WHERE project_id = 1;
```

## Тестовые данные

`backend/scripts/seed_demo.sql` создаёт обезличенный пилот: 8 блоков графа, 9 связей, 8 проверок с интервалом 60 с и историю за 30 дней — 345 582 результата, около 30 МБ. Около 2 % результатов — warn или fail. У «Погода API» нет данных последние 20 минут, у «POS-система» последний результат — сбой.

```bash
alembic upgrade head
psql "$DATABASE_URL_PSQL" -f backend/scripts/seed_demo.sql
```

Результаты вставляются в хронологическом порядке, как они приходят в реальной системе. После загрузки выполняется `VACUUM (ANALYZE)`.

## Анализ запроса «последний результат каждой проверки»

Это ключевой запрос представления, его выполняет каждое обновление графа. Замеры — `EXPLAIN (ANALYZE, BUFFERS)` на PostgreSQL 16.10 с тестовыми данными.

| № | Вариант запроса | Индексы | План | Время |
|---|---|---|---|---|
| 1 | `DISTINCT ON (health_check_id) ... ORDER BY health_check_id, checked_at DESC` | отдельные B-tree по `health_check_id` и `checked_at` (миграция 0001) | Seq Scan по 345 582 строкам и сортировка на диске (external merge, 8,8 МБ) | 329,6 мс |
| 2 | `LEFT JOIN LATERAL (... ORDER BY checked_at DESC LIMIT 1)`, все проверки свежие | те же | Index Scan Backward по `checked_at` с фильтром по проверке | 0,17 мс |
| 3 | то же, одна проверка молчит 25 дней | те же | тот же план, но фильтр отбрасывает 32 014 строк на каждую проверку | 49,8 мс |
| 4 | DISTINCT ON | составной `(health_check_id, checked_at DESC)` | Index Scan по составному индексу, без сортировки, но по всем строкам | 94,0 мс |
| 5 | LATERAL, одна проверка молчит 25 дней | составной + BRIN | Index Scan по составному индексу с условием `health_check_id = hc.id`, по 1 строке на проверку | 0,19 мс |

Выводы:

1. **DISTINCT ON** читает всю таблицу при любом индексе, и время растёт вместе с историей. Для представления выбран LATERAL с `LIMIT 1`.
2. **Ловушка планировщика.** С отдельным индексом по `checked_at` LATERAL быстрый только пока все проверки свежие (вариант 2). Если проверка замолчала (а это ровно тот случай, ради которого строится граф), обратный проход по времени перебирает чужие строки (вариант 3). Даже после создания составного индекса планировщик продолжал выбирать B-tree по `checked_at`: при `LIMIT 1` он считает, что подходящая строка найдётся почти сразу.
3. **Решение (миграция 0002).** Составной B-tree `(health_check_id, checked_at DESC)` отвечает на «последний результат проверки» одним спуском по индексу. Одиночный B-tree по `health_check_id` удалён: его покрывает префикс составного. B-tree по `checked_at` заменён на BRIN.

## Выборка за период: BRIN

Отчёты (сбои за сутки, доступность за неделю) фильтруют по времени по всем проверкам. Таблица пополняется только в хронологическом порядке, поэтому физический порядок строк совпадает с `checked_at`. Для такого случая подходит BRIN: он хранит минимум и максимум на диапазон страниц.

| Индекс | Размер |
|---|---|
| `check_result_pkey` (B-tree) | 7,6 МБ |
| `ix_check_result_check_time` (B-tree, составной) | 19 МБ |
| `ix_check_result_checked_at_brin` (BRIN) | 24 кБ |

Сбои за последние сутки: Bitmap Heap Scan по BRIN, просмотрено 154 из 2 202 страниц, **8,4 мс**.

Найденная особенность: индекс, созданный миграцией на пустой таблице, не обобщает новые диапазоны страниц сам. Необобщённые диапазоны всегда считаются совпавшими, и запрос за сутки читал 2 074 страницы за 96,8 мс. Поэтому BRIN создаётся с `autosummarize = on` (новые диапазоны обобщает autovacuum), а после массовой загрузки выполняется `VACUUM`.
