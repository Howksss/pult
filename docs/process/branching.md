# Модель ветвления и правила работы с кодом

## Модель

Упрощённый GitHub Flow: одна долгоживущая ветка `main`, она всегда в рабочем состоянии и по умолчанию. Каждая задача из трекера делается в своей короткой ветке и попадает в `main` только через pull request.

Почему не Git Flow: у проекта нет параллельно поддерживаемых версий и плановых релизных циклов, поэтому ветки `develop`, `release/*` и `hotfix/*` только добавят слияний. Релиз — это аннотированный тег на `main`.

## Ветки

Формат: `<тип>/<номер задачи>-<краткое-описание>`, латиницей через дефис.

| Тип | Когда |
|---|---|
| `feature/` | новая функциональность |
| `fix/` | исправление ошибки |
| `docs/` | документация |
| `ci/` | конвейер CI/CD |
| `chore/` | обслуживание: зависимости, версии, релизы |

Пример: `feature/3-health-check`.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): `<тип>(#<задача>): <что сделано>`. Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `ci`, `chore`.

Пример: `feat(#3): эндпоинт health-check`.

## Pull request

- Один pull request на одну задачу, описание по шаблону `.github/pull_request_template.md`: закрываемая задача, что и зачем сделано, как проверить локально, риски.
- Перед слиянием: зелёные проверки `backend` и `frontend` и одобрение ревьюера.
- Конфликты с `main` автор решает у себя: `git merge main` в своей ветке, затем push.
- Способ слияния — merge commit, чтобы в истории `main` оставалась граница каждого pull request.

## Защита main

- прямые push в `main` запрещены;
- слияние только через pull request с одним одобрением;
- обязательны успешные проверки `backend` и `frontend`, ветка должна быть актуальной относительно `main`;
- запрещены force push и удаление ветки.

## Версии

[Семантическое версионирование](https://semver.org/lang/ru/). До первого рабочего прототипа версии идут как `0.y.z`. Журнал изменений ведётся в `CHANGELOG.md` по формату [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
