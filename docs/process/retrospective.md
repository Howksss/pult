# Ретроспектива итерации 0.1.0

Итерация: задачи #3–#8 и #15, pull request #9–#14 и #16. Команда — один участник.

## Что получилось

- Каждая задача из трекера сделана в своей ветке и влита через pull request со ссылкой `Closes #N`. Задачи закрылись автоматически при слиянии.
- Ко всем пяти функциональным pull request есть ревью с замечаниями к конкретным строкам. Каждое замечание исправлено отдельным коммитом, обсуждение закрыто.
- CI появился первым (PR #9), поэтому все последующие изменения проверялись автоматически.
- Конфликт между #3 и #4 разрешён осознанно: сохранены обе правки, после слияния прогнаны тесты.
- История `main` оформлена по Conventional Commits, у каждого pull request есть merge-коммит.

## Трудности

| Что произошло | Как решили |
|---|---|
| GitHub не даёт автору одобрить собственный pull request, а в команде один человек. | Правило «одно одобрение» включено. Ревью оформлено комментариями к строкам с предложенными правками. Сливает владелец репозитория в обход правила. |
| Классическая защита ветки с `enforce_admins = false` разрешала владельцу прямой push в main. | Перешли на ruleset: владелец может обойти правила только при слиянии pull request. Проверка: прямой push отклоняется с ошибкой GH013. |
| Обязательные проверки `backend` и `frontend` нельзя включить, пока workflow нет в main. | Первым влит PR с CI, затем проверки сделаны обязательными. |
| PR #10 и #12 влиты до того, как отчитались проверки их последнего коммита. Обход правил отключает и обязательные проверки, а скрипт ожидания для #12 прочитал SHA ветки до того, как GitHub его обновил, и увидел зелёные проверки предыдущего коммита. | Для #10 прогон завершился успешно. Прогон #12 GitHub отменил после слияния, но изменения проверены: они вошли в следующий коммит main (слияние #13), и его CI зелёный. Теперь скрипт сначала сверяет SHA ветки с отправленным коммитом, потом ждёт проверки. |
| У слияний #11 и #12 в main стоят отменённые прогоны. | Так работает `concurrency`: новый push в main отменяет незавершённый прогон, и проверяется последний коммит. Проверка main зелёная на каждом релизном коммите. |
| Ветки #3 и #4 дописывали строки в одно и то же место `main.py` и README. | Объединили обе правки: сначала CORS, затем роутер. В README оставлены оба пояснения. |
| Режим «ветка должна быть актуальна относительно main» требует перед каждым слиянием влить main в ветку. | Принято как цена за гарантию, что тесты прошли на итоговом коде. |

## Выводы на следующие итерации

1. С появлением второго участника убрать обход правил: одобрение и проверки обязательны для всех.
2. Включать обязательные проверки в тот же день, когда появился CI.
3. Сливать pull request только после зелёных проверок именно того коммита, который отправлен последним, а не просто «зелёного PR».
4. Общие точки входа (`main.py`, README) менять отдельными небольшими pull request и чаще синхронизироваться с main.
5. Если merge-коммиты обновления от main начнут мешать читать историю, перейти на squash-merge.
