# Работа с ИИ-ассистентами

В проекте ИИ встречается в двух ролях:

1. **Ассистент разработчика** — помогает писать и проверять код самого Pult. Этот документ — про него.
2. **Агент внутри продукта** — правит код системы клиента по задаче из чата блока. Его ограничения описаны в [ADR 002](../adr/002_agent_changes_via_pull_request.md) и [ADR 003](../adr/003_llm_provider.md).

## Инструменты

| Инструмент | Тип | Сильные стороны | Ограничения |
|---|---|---|---|
| GitHub Copilot | Автодополнение и чат в IDE | Быстрые подсказки в строке, знает контекст открытых файлов | Видит мало контекста проекта, легко принять неверную строку |
| Claude Code | Агент в терминале | Работает со всем репозиторием, запускает тесты и линтеры, объясняет решения | Нужен контроль: может изменить больше, чем просили |
| Cursor | IDE со встроенным ИИ | Правка нескольких файлов, чат с кодовой базой | Отдельная IDE, настройки проекта приходится дублировать |
| ChatGPT / Claude в браузере | Чат | Объяснение концепций, разбор ошибок | Нет доступа к коду, легко передать лишнее |

## Где ассистент полезен

- Черновики тестов и поиск граничных случаев по требованию.
- Объяснение незнакомого кода, библиотеки или сообщения об ошибке.
- Предварительное ревью diff перед открытием pull request.
- Рутинный рефакторинг по образцу, который потом проверяют тесты.
- Черновики документации и описаний pull request.

## Правила

1. **Автор отвечает за каждую строку.** Код, предложенный ассистентом, принимается, только если автор может объяснить, что он делает и почему так.
2. **Тот же контроль качества.** Сгенерированный код проходит те же проверки, что и написанный вручную: Ruff, mypy, ESLint, тесты с порогом покрытия, ревью. Исключений нет.
3. **Тест до принятия.** Изменение поведения без теста, который это поведение проверяет, не принимается.
4. **Никаких секретов и данных заказчика в запросах.** Не передавать файлы `.env`, токены, ключи, логи с персональными данными, код и данные пилотной системы. Автоматически от попадания секретов в репозиторий защищают `.gitignore` (файлы `.env`) и хук `detect-private-key`. Запросы к ассистенту автоматически не проверяются, здесь контроль только ручной.
5. **Проверять версии API.** Ассистент может предложить устаревший вызов библиотеки. Сверять с документацией той версии, которая закреплена в `requirements.txt` и `package.json`.
6. **Мелкими шагами.** Просить одно изменение за раз и смотреть diff, а не принимать правку десятка файлов целиком.

## Риски и меры

| Риск | Пример | Мера |
|---|---|---|
| Выдуманный или устаревший API | Параметр, удалённый в новой версии SDK | Сверка с документацией, mypy и тесты в CI |
| Утечка данных | Логи пилотной системы вставлены в чат | Правило 4, при необходимости обезличенный пример |
| Незаметная регрессия | Правка «заодно» соседней функции | Мелкие шаги, ревью diff, порог покрытия |
| Уязвимый код | Сборка SQL-запроса через строки | Правила Ruff `S` (bandit), ORM, сканирование в CI (ПР9) |
| Лицензии | Дословный фрагмент из чужого проекта | Не принимать крупные фрагменты без понимания источника |
| Потеря навыка | Автор не понимает собственный код | Правило 1: объяснить каждую строку на ревью |

## Порядок работы на примере

Задача: найти граничные случаи для `block_status` (FR-09).

1. Ассистенту передаются только сигнатура функции и текст требования. Данные заказчика не передаются.
2. Предложенные случаи сверяются с требованием. Ошибочные отбрасываются: например, «при отсутствии данных — ok» противоречит FR-09.
3. Подходящие случаи оформляются как наборы в параметризованном тесте, тесты запускаются.
4. Изменение проходит pull request с ревью и CI, как любое другое.
