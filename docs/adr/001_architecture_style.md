# ADR 001. Модульный монолит с отдельным процессом-воркером

- Статус: принято
- Дата: 2026-10-21

## Контекст

- Проект разрабатывает один человек, требования будут меняться после показа пилотному заказчику.
- Нагрузка небольшая: по [NFR-M1](../requirements/non_functional.md) это 20 проектов по 100 блоков на одном сервере 2 vCPU / 4 ГБ.
- Работа делится на два вида. Короткие запросы интерфейса (граф, статусы, чат) должны отвечать за сотни миллисекунд. Длинные фоновые операции идут в фоне: задача агента может длиться минуты, сбор статусов работает по таймеру.
- Журнал аудита должен записываться в одной транзакции с действием, которое он описывает.

Рассмотренные варианты:

1. **Микросервисы**: отдельные сервисы графа, мониторинга, агента и аудита, брокер сообщений (RabbitMQ или Kafka).
2. **Монолит с выполнением всего в процессе API**: задачи агента запускаются в фоновых задачах FastAPI.
3. **Модульный монолит, два типа процессов**: одна кодовая база и одна база данных. Процесс `api` обслуживает HTTP, процесс `worker` выполняет задачи агента и сбор статусов.

## Решение

Выбран вариант 3.

- Код делится на модули с явными границами: `graph`, `health`, `agent`, `review`, `audit`. Модуль обращается к другому только через его сервисный интерфейс, а не к чужим таблицам напрямую.
- Один Docker-образ backend запускается в двух ролях: `api` (uvicorn) и `worker`.
- Очередь задач хранится в PostgreSQL: таблица `agent_task`, выборка через `SELECT … FOR UPDATE SKIP LOCKED`. Отдельный брокер не нужен.
- Обновления статусов и поток ответов агента доходят до интерфейса через Server-Sent Events. Воркер публикует события в PostgreSQL через `LISTEN/NOTIFY`.

## Последствия

Плюсы:

- Развёртывание — один `docker compose` из четырёх контейнеров: db, api, worker, frontend.
- Действие и запись аудита фиксируются в одной транзакции.
- Длинная задача агента не держит HTTP-воркеры и не мешает интерфейсу.
- Можно запустить несколько воркеров без изменения кода ([NFR-M2](../requirements/non_functional.md)).

Минусы и риски:

- `api` и `worker` масштабируются только целиком, по отдельным модулям нельзя.
- Очередь в PostgreSQL рассчитана на сотни задач в час, не на тысячи в секунду. При росте нагрузки модуль `agent` выносится в отдельный сервис. Его интерфейс уже отделён, поэтому менять придётся вызов, а не логику.
- Чтобы границы модулей соблюдались, их нужно проверять при ревью (позже — линтером импортов).
