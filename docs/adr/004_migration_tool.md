# ADR 004. Alembic как инструмент миграций схемы

- Статус: принято
- Дата: 2026-11-24
- Дополняет выбор СУБД из практической работы № 2: PostgreSQL 16 ([модель данных](../data/README.md), [ADR 001](001_architecture_style.md)).

Номер 004, а не 002: записи 002 и 003 в журнале уже заняты, а принятые записи не переписываются.

## Контекст

Схема создаётся и меняется только миграциями. Ручные правки в DBeaver или pgAdmin запрещены, потому что их нельзя повторить на другой базе и откатить. Требования к инструменту:

- миграции лежат в репозитории рядом с кодом, проходят ревью в pull request и применяются одной командой в CI и на сервере;
- у каждой миграции есть откат;
- можно сверить схему базы с моделями приложения и поймать расхождение до слияния;
- можно выполнить произвольный SQL: представление `v_block_status`, индекс BRIN, частичный уникальный индекс, `COMMENT ON`, новые значения `ENUM` вне транзакции.

Рассмотренные варианты:

1. **Alembic** — инструмент миграций SQLAlchemy, миграции на Python.
2. **Flyway** — миграции на чистом SQL, запускается на JVM или из образа Docker.
3. **Liquibase** — миграции в XML, YAML или SQL с журналом изменений, запускается на JVM.

## Решение

Выбран Alembic 1.14.

- Модели SQLAlchemy в `backend/app/models` — общий источник для кода и миграций. Черновик миграции строится `alembic revision --autogenerate` и правится руками.
- Миграции лежат в `backend/migrations/versions` и нумеруются по порядку: `0001`, `0002` и далее. Настройки — `backend/alembic.ini` и `backend/migrations/env.py`, адрес базы берётся из переменной `DATABASE_URL`, а не из файла.
- На сервере миграции применяет отдельный сервис `migrate` в `deploy/docker-compose.yml` до запуска `api` и `worker`.
- Тестовые данные загружает миграция `0010` по флагу: `alembic -x seed=demo upgrade head`. Без флага, в том числе на рабочем сервере, она ничего не делает.
- CI на каждый pull request разворачивает схему на пустой базе, повторяет то же на второй базе и сверяет обе (`deploy/db/verify.sh`), откатывает новые миграции и применяет их снова. Тест `test_schema_after_migrations_matches_models` сравнивает схему после миграций с моделями.

## Последствия

Плюсы:

- Нет второго языка и второй среды выполнения: миграции написаны на том же Python, что и backend, и запускаются из того же образа.
- Расхождение моделей и схемы ловится автоматически (`compare_metadata` в тестах).
- Сложные шаги, например перенос данных или удаление дубликатов перед `UNIQUE`, пишутся на Python и SQL в одной миграции (`0005`, `0007`).

Минусы и риски:

- Автогенерация не видит `CHECK`, представления и изменения `ENUM`. Их пишем руками, а проверяют их тесты `test_pg_schema.py`. Комментарии `COMMENT ON` ведутся миграциями, а не моделями, поэтому `env.py` исключает их из сравнения (`alembic check`), а полноту комментариев проверяет отдельный тест.
- Порядок миграций держится на `down_revision`. Две ветки с миграцией одного номера дадут две «головы». CI это поймает, потому что `alembic upgrade head` с двумя головами завершается ошибкой. Тогда вторую миграцию перенумеровываем до слияния.
- Откат миграции, которая удаляет данные, их не вернёт. Перед выкаткой на сервере снимается копия БД ([инструкция](../module5/backup_instructions.md)).
