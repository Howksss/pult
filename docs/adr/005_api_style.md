# ADR 005. REST как базовый стиль API

- Статус: принято
- Дата: 2026-11-25

## Контекст

У API Pult три вида потребителей:

- интерфейс на React: граф, панели блока, настройка проверок;
- probe на сервере клиента: присылает результаты проверок пачками раз в минуту;
- интеграции: n8n для ежедневной сводки ([low-code](../lowcode/README.md)), скрипты выгрузки, коллекция Bruno.

Данные — сущности с жизненным циклом из ER-модели: проекты, участники, блоки, связи, проверки, результаты, области доступа, API-ключи. Операции над ними — создать, прочитать, найти по фильтру, изменить, удалить. Переходы состояния (проверка включена или выключена, запуск проверки вне расписания) немногочисленны.

Требования к стилю: контракт пишется до кода и проверяется автоматически, mock-сервер по контракту для тестировщиков, понятные коды ошибок, работа через обычный HTTPS без своего клиента, кэширование и повтор запросов прокси и библиотеками.

Рассмотренные варианты:

1. **REST поверх HTTP с JSON** и контрактом OpenAPI.
2. **GraphQL**: клиент сам выбирает поля, одна точка входа.
3. **gRPC**: строгий контракт Protobuf, двоичный протокол, HTTP/2.

## Решение

Базовый стиль — REST, контракт `docs/api/openapi.yaml` (OpenAPI 3.1).

- Ресурсы — существительные во множественном числе, идентификатор в пути, вложенность не глубже двух уровней: `/projects/{id}/blocks`, а блок дальше адресуется сам — `/blocks/{id}`.
- Методы по семантике HTTP: `POST` создаёт, `GET` читает, `PUT` заменяет целиком (область блока), `PATCH` меняет часть, `DELETE` удаляет. `GET`, `PUT`, `DELETE` идемпотентны. Повтор `POST` не создаёт дубликат: уникальность (имя блока, связь, путь области, проект на репозиторий у пользователя) даёт 409, повтор пачки probe пропускается.
- Действия, которые не сводятся к изменению полей, — подресурс с глаголом через `POST`: `POST /checks/{id}/run`.
- Фильтры и пагинация — в параметрах запроса (`?kind=bot&limit=50&offset=100`), общее число — в заголовке `X-Total-Count`.
- Ошибки — `application/problem+json` по RFC 9457, коды различают синтаксис (400), аутентификацию (401), права (403), отсутствие (404), конфликт (409) и нарушение схемы (422).
- Аутентификация: cookie сессии для интерфейса, `X-API-Key` для интеграций, `X-Probe-Token` для probe.
- Версия в пути `/api/v1`. Совместимые изменения — новые поля и операции в v1, несовместимые — `/api/v2` ([журнал изменений](../api/changelog.md)).

OpenAPI 3.1, а не 3.0: 3.1 — текущая версия той же ветки 3.x, схемы в ней — обычный JSON Schema 2020-12. Тесты backend проверяют ответы тем же валидатором JSON Schema, а Redocly, Redoc, Prism и Bruno 3.1 поддерживают.

Направления развития, когда появится задача:

- **Server-Sent Events или WebSocket для уведомлений.** Сейчас интерфейс опрашивает граф раз в 10 с. Когда агент будет отвечать по мере генерации (FR-17), поток ответа и смена статусов пойдут через SSE: события идут только от сервера, SSE работает через тот же HTTPS и прокси. WebSocket нужен, если появится двусторонний обмен, например совместное редактирование доски.
- **Очередь сообщений для событийной интеграции.** Результаты probe сейчас принимаются синхронно. Если клиентов станет много и пачки пойдут потоком, приём будет класть их в очередь (PostgreSQL `LISTEN/NOTIFY` или Redis Streams), а пересчёт статусов и уведомления — разбирать очередь. Внешним системам Pult сможет отдавать события «блок упал» и «блок восстановился» через вебхуки.
- GraphQL и gRPC не нужны: у нас нет клиентов, которым не хватает фиксированных ответов, и нет межсервисного трафика, где важна двоичная передача.

## Последствия

Плюсы:

- Каждый ответ сверяется с контрактом в тестах, а mock-сервер Prism отвечает по тому же контракту, пока реализации нет.
- Любая интеграция работает через `curl` и стандартные библиотеки, n8n и Bruno подключаются без кода.
- Коды ответов и формат ошибок одинаковы во всех операциях.

Минусы и риски:

- Экран может собираться из нескольких запросов: граф, затем проверки блока. Пока данных мало, это не заметно. Если станет заметно, добавим агрегирующий ресурс, а не GraphQL.
- Опрос раз в 10 с даёт задержку статуса до 10 с, пока нет SSE.
- Пагинация `limit`/`offset` на больших смещениях медленнее курсорной. История результатов растёт быстрее всего, и при росте её пагинацию переведём на курсор по `checked_at`.
